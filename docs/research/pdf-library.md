# Библиотека PDF: jsPDF или pdf-lib

Исследование к issue [#4](https://github.com/alexrehtide/knitting/issues/4). Контекст — раздел «PDF» в [spec.md](../spec.md): векторный PDF, листы A4/A3 в двух ориентациях, линейки, ч/б **узоры заливки** нитей, **легенда**, русский текст, схема до 500×500 клеток, всё в браузере.

Дата: 2026-10-25. Версии: jsPDF 4.2.1, pdf-lib 1.17.1 + @pdf-lib/fontkit 1.1.1, @cantoo/pdf-lib 2.11.1, pdfkit 0.20.2.

## Вывод

**Берём jsPDF 4.x.** Только у него из двух кандидатов есть публичный API тайловых узоров (`TilingPattern`), он активно поддерживается, даёт самый маленький бандл и в замере собирает худший случай (500×500, цвет+узор, 140 листов A4) примерно за 1,2 с. pdf-lib тоже справляется, но узоры пришлось бы собирать из низкоуровневых объектов PDF руками, а сам проект не выпускал релизов с ноября 2021 года.

Две оговорки при работе с jsPDF:

1. Узор ставить через `fill({ key })` **без** `matrix`. С `matrix` jsPDF на каждый вызов создаёт копию узора, и на 250 тыс. клеток сборка растягивается на десятки минут (см. «Подводные камни»).
2. Шрифт брать TTF с кириллицей под лицензией OFL и загружать лениво вместе с jsPDF. jsPDF урезает шрифт до использованных глифов хуже, чем fontkit: в PDF остаётся 77–92 КБ против 11–20 КБ. Для нашей задачи это допустимо.

## Узоры заливки

В PDF узор нити естественно задаётся **тайловым узором** (PatternType 1): ячейка рисуется один раз и повторяется с шагом XStep/YStep. Координаты узора задаются в системе координат страницы по умолчанию (ISO 32000-1, §8.7.3), поэтому штриховка соседних клеток одной нити совпадает и складывается в непрерывную область. Это лучше, чем рисовать узор отдельно в каждой клетке, и намного компактнее.

- **jsPDF.** API документирован и типизирован (`types/index.d.ts`): `new TilingPattern(bbox, xStep, yStep, gState?, matrix?)`, `beginTilingPattern(p)`, обычные команды рисования, `endTilingPattern(key, p)`, затем `fill({ key })`, `fillEvenOdd`, `fillStroke`. Работает только внутри `doc.advancedAPI(...)` [1]. Масштаб узора передаётся в `matrix` **конструктора**, а не при заливке.
- **pdf-lib.** API узоров нет. В замере работает такой обход: поток узора создаётся через `doc.context.flateStream(ops, { Type: 'Pattern', PatternType: 1, ... })`, словарь `/Pattern` пишется в `page.node.Resources()`, заливка — через `PDFOperator.of('cs', [Pattern])` и `PDFOperator.of('scn', [/P0])`. Это рабочий, но приватный по духу слой: строки операторов пришлось бы поддерживать самим.
- **Рисовать вручную** (линии, отсечённые по клетке, в каждой клетке) возможно в обеих библиотеках. Но это раздувает файл и замедляет сборку: в pdf-lib 7,3 МБ и 10,8 с против 2,7 МБ и 2,1 с с тайловыми узорами.

## Замер производительности

Сценарий худшего случая: 500×500 клеток по 5 мм, лист A4 книжный (36×52 клетки) — 140 листов. Каждая клетка залита цветом и одним из 16 узоров, на каждом листе есть строка русского текста, шрифт Arial встроен. Node 24 на Windows 11; в браузере цифры будут того же порядка. Скрипты лежали во временной папке, в репозиторий не входят.

| Вариант | Сборка | Сохранение | Размер |
|---|---|---|---|
| jsPDF, цвет+узор, `fill({ key })` | 0,56 с | 0,67 с | 1,8 МБ |
| jsPDF, только цвет | 0,35 с | 0,33 с | 1,0 МБ |
| jsPDF, `fill({ key, matrix })` | > 10 мин, прерван | — | — |
| pdf-lib, цвет+узор (тайловые, операторы пачкой на лист) | 0,98 с | 1,11 с | 2,7 МБ |
| pdf-lib, только цвет, `drawRectangle` на клетку | 2,56 с | 1,57 с | 1,9 МБ |
| pdf-lib, цвет + ручная штриховка с clip на клетку | 4,72 с | 6,07 с | 7,3 МБ |

Все файлы открываются в pdf.js (`pdfjs-dist` 4.10): 140 страниц, русский текст извлекается правильно (`«Олень»`, `–`, `×`). Значит, ToUnicode у обеих библиотек корректен. Визуально узоры не проверялись — это задача прототипа.

Резерв: если клетки одной нити объединять в один путь на лист (несколько `rect(..., null)` и затем один `fill`), число операторов и размер файла заметно уменьшатся. Заодно пропадут тонкие «швы» от сглаживания между соседними прямоугольниками в просмотрщиках.

## Шрифт с кириллицей

- **jsPDF:** README прямо говорит, что 14 стандартных шрифтов PDF ограничены ASCII и для UTF-8 нужен свой `.ttf` [3]. Шрифт передаётся base64-строкой: `addFileToVFS` + `addFont`. В исходниках есть урезание до использованных глифов (`font.metadata.subset.encode(glyIdsUsed)`) [4], но таблицы шрифта остаются крупнее, чем у fontkit. Жирное начертание для заголовка и легенды — второй TTF.
- **pdf-lib:** для своих шрифтов обязателен @pdf-lib/fontkit [5]. Сам fontkit весит около 360 КБ gzip, то есть больше всей jsPDF. С `subset: true` у fontkit есть открытые ошибки урезания: пропадают символы в японском (#1232), шрифт ломается на тексте с дефисом (#1396) [7]. В нашем замере кириллица, «», – и × вывелись правильно.
- **Вес для пользователя.** Скачивается исходный TTF, а не результат урезания. Поэтому шрифт стоит заранее, на этапе сборки, урезать до латиницы, кириллицы и нужной пунктуации (например, `pyftsubset`) и подключать как отдельный ассет, который грузится только при экспорте. Подойдёт любой OFL-шрифт с кириллицей, у которого есть TTF (с TrueType-контурами) в начертаниях Regular и Bold. Системные шрифты (Arial, Segoe UI) использовались только для замера: распространять их нельзя.

## Бандл и ленивая загрузка

Замер: esbuild 0.24, `--bundle --minify`, браузерная платформа, импорт главного класса.

| Пакет | min | min+gzip |
|---|---|---|
| jspdf (canvg/html2canvas/dompurify вынесены) | 408 КБ | 133 КБ |
| pdf-lib | 421 КБ | 175 КБ |
| pdf-lib + @pdf-lib/fontkit | 1338 КБ | 535 КБ |
| pdfkit (браузерная сборка) | 521 КБ | 209 КБ |

У jsPDF есть необязательные зависимости (`html2canvas`, `dompurify`, `canvg`). Они нужны только для `html()`/SVG и подгружаются динамическим импортом [3]. Метод `html()` нам не нужен, поэтому в Vite их стоит пометить как external или не устанавливать: тогда лишних чанков не будет. Генератор PDF лежит в слое infrastructure за портом, поэтому его можно загружать через `await import('jspdf')` в момент экспорта, а шрифт — через `fetch` ассета. Начальная загрузка редактора их не включает.

## Подводные камни jsPDF

- **`fill({ key, matrix })` даёт квадратичную сложность.** В `src/jspdf.js` (v4.2.1, около строки 4400) стоит комментарий: «we cannot apply a matrix to the pattern on use so we must abuse the pattern matrix and create new instances for each use». На каждый такой вызов `cloneTilingPattern` добавляет новый объект узора, а `addPattern` для каждого считает `Object.keys(patterns).length` [4]. Поэтому `matrix` задаётся один раз в конструкторе `TilingPattern`.
- **Advanced API.** Узоры работают только внутри `advancedAPI`. В этом режиме у `rect` стиль `null` означает «только путь», а заливка делается отдельным вызовом `fill()` (`putStyle` в исходниках) [4].
- **Безопасность.** Релиз 4.0.0 закрыл уязвимость path traversal (GHSA-f8cm-6447-x5h2), но только в Node-сборке: доступ к файловой системе по умолчанию запрещён [6]. В браузере это нас не затрагивает, но стоит держать версию ≥ 4.

## Другие варианты, кратко

- **@cantoo/pdf-lib** — живой форк pdf-lib (2.11.1, сентябрь 2026, 356 ★, MIT) [8]. Чинит заброшенность, но тайловых узоров в публичном API (`PDFPage`) тоже нет, а бандл больше (252 КБ gzip только у ESM-сборки самой библиотеки). Явно лучше jsPDF для нас он не становится.
- **pdfkit** — MIT, активен (0.20.2, сентябрь 2026; 10,7 тыс. ★), встроенный fontkit с хорошим урезанием шрифтов, браузерная сборка (209 КБ gzip), тайловые узоры — по CHANGELOG [9]. Это серьёзная альтернатива. Но поддержка узоров не описана в документации (`docs/vector.md`), API потоковый в духе Node, а в последних версиях были ломающие изменения браузерной сборки (убран `virtual-fs`, стандартные шрифты регистрируются вручную). Если jsPDF подведёт в прототипе, переходить стоит на него, а не на pdf-lib.

## Что проверить в прототипе

- Как 16 ч/б узоров выглядят в Acrobat, Chrome (PDFium), Firefox (pdf.js) и на реальном ч/б принтере, особенно тонкие линии при печати.
- Нет ли швов между клетками; при необходимости объединять клетки одной нити в один путь.
- Время экспорта 500×500 в браузере и нужна ли индикация прогресса или Web Worker. jsPDF не зависит от DOM, так что работу в воркере стоит проверить.
